# Parity Monitor — Design Spec (Pre-Registered)

Date: 2026-07-21. Status: DRAFT — awaiting user approval before build.
Companion to the self-auditing system discussion; this is its first and most
valuable component. Discipline: thresholds frozen here, before any check runs;
amendments require a dated decision-log entry.

---

## 1. Problem statement

Every failure in this project's history shared one shape: **the machine broke
silently while looking normal.**

| incident | silent for | would parity catch it? |
|---|---|---|
| Signal enum bug — 444 runs, zero trades | ~3 months | day 1-3 (trade-rate check) |
| Placeholder enctoken — all fetches HTTP 400 | 5+ weeks | day 1 (liveness + data checks) |
| fib_3wave structurally unable to fire | forever | week 1 (trade-rate check) |
| TOTP re-login loop every 5 min | hours | day 1 (auth-event count) |
| Entries after square-off holding overnight | 1 day | day 1 (position-at-close check) |
| Missed July rebalance (empty daily cache) | would've been 1 month | day 1 (rebalance-event check) |

The monitor's sole job: make silence impossible. Every strategy carries a
frozen "Expectation Book" from its backtest; every evening a pure-arithmetic
script compares the day's reality against it and reports GREEN/AMBER/RED.
No AI anywhere in the loop — a smoke detector must be deterministic.

## 2. Non-goals

- Never places, modifies, or exits trades. Only side-effects: Telegram
  messages and writing `strategies_paused.json` (which the live monitor
  already consults before ENTRIES only).
- Not a performance judge. Its thresholds detect *implementation breakage*
  (behavior ≠ backtest), not *edge decay* (that's the monthly scorecard's
  job, out of scope for v1).
- No auto-unpause. A human clears every RED.

## 3. Components

### 3.1 Expectation Book (`kite/live_monitor/expectations/<strategy>.json`)

One frozen JSON per live strategy, generated by `gen_expectations.py` from the
strategy's own validation backtest (honest_lab for momo_rotation_63,
retest_all for the swing candidates, walkforward sample for the intraday
incubator set — wide bands where the backtest was weak, because these cards
detect bugs, not judge alpha):

```json
{
  "strategy": "momo_rotation_63",
  "book": "main",
  "cadence": "monthly",
  "trades_per_month": {"lambda": 4.6, "hard_min_window_days": 45},
  "win_rate": {"p": 0.42, "n_backtest": 199},
  "avg_win_pct": 7.1, "avg_loss_pct": -3.4,
  "max_drawdown_pct": -29.7,
  "hold_days": {"p50": 31, "p95": 92},
  "slippage_assumed_pct": 0.05,
  "generated": "2026-07-21", "source": "honest_lab ext 2015-2026"
}
```

Regenerating a card requires a git commit (cards are tracked files) — no
silent expectation drift.

### 3.2 Nightly check run (`kite/live_monitor/parity_monitor.py`)

Runs on Oracle via systemd timer at **16:15 IST Mon-Fri** (after EOD close and
daily summary). Reads: both paper-trade DBs, expectation JSONs, monitor.log
tail, `data/momo_rotation_state.json`, announcement-filter status. Writes:
one Telegram line (always), `parity_history.jsonl` (always), and
`strategies_paused.json` (on RED with pause action).

### 3.3 Checks and frozen thresholds

| # | check | applies to | AMBER | RED | RED action |
|---|---|---|---|---|---|
| P1 | **Liveness**: scan cycles logged today (market day) | system | — | zero cycles | alert (nothing to pause — monitor is dead) |
| P2 | **Data freshness**: daily cache count at swing scan | system | <90% of universe | <50% | alert |
| P14 | **Wide-universe data freshness**: `load_wide_daily_data()` cache count (679-stock swing-candidate universe) at swing scan; line absent entirely on a market day → RED | system | <90% of universe *(reuses P2's threshold — see 2026-07-27 decision log)* | <50% *(reuses P2's threshold)* | alert |
| P3 | **Trade rate**: Poisson two-tail prob of observed trade count vs λ over rolling 20 trading days (intraday/swing strategies only) | per strategy | p<0.05 | p<0.01 | pause entries |
| P4 | **Cadence events**: momo rebalance occurred within first 3 trading days of month; EOD square-off left zero INTRADAY positions open past 15:30 | momo / books | — | violated | alert (+pause for repeat) |
| P5 | **Win rate**: once live N≥60 closed trades — two-proportion z-test live vs card | per strategy | p<0.05 | p<0.01 | pause entries |
| P6 | **Drawdown**: live equity DD vs card max_drawdown | per book | >1.5× | >2.0× | pause entries |
| P7 | **Hold time**: live p50 hold vs card p95 | per strategy | p50 > card p95 | — | amber only |
| P8 | **Slippage/fill sanity**: paper fill price vs same-day candle range (fill outside [low,high] = impossible fill) | per trade | 1 event | ≥2 events/week | pause entries (harness bug) |
| P9 | **Auth events**: "Login successful" count in today's log | system | >3 | >10 | alert (login loop) |
| P10 | **Ann-filter**: refresh failed | system | 1 day | ≥3 consecutive days | alert |
| P11 | **Ann-filter category drift**: 0 red-flag matches across universe for 15 consecutive market days (historical base rate ≈ daily) | system | — | triggered | alert (category likely renamed) |
| P12 | **Parity dead-man**: parity_history.jsonl last entry age, checked by the NEXT run; plus the daily line itself is the human-visible heartbeat | self | — | gap > 1 market day | noted in next report |

N-gates: P3 activates after 10 trading days of a strategy's live history; P5
after 60 closed trades; P6 after 20 trading days. Before gates: reported as
"warming up", never colored.

### 3.4 Output contract

- **Daily, always, exactly one Telegram line** (the dead-man heartbeat):
  `🩺 parity: 5 strategies green` or
  `🩺 parity: RED momo_rotation_63 (trade-rate p=0.003) — entries paused; 4 green`.
- AMBERs: included in the daily line only as a count; details in Saturday
  digest (with the week's history) to avoid alert fatigue.
- REDs: immediate detail line + action taken + what a human should check.
- Everything appended to `parity_history.jsonl` for the future monthly
  scorecard to consume.

### 3.5 Pause mechanics

`strategies_paused.json`: `{"momo_rotation_63": {"reason": "...", "since": "..."}}`.
Live monitor consults it before entries (30-line hook, same pattern as the
announcement filter). Exits and stop-losses are NEVER paused. Unpause =
human deletes the entry (or tells Claude to). Every pause/unpause appended to
parity_history.jsonl.

## 4. Build plan

| step | what | effort |
|---|---|---|
| 1 | `gen_expectations.py` + 7 cards (momo, 2 swing candidates, 4 incubator) committed | ~1 hr |
| 2 | `parity_monitor.py` checks P1-P12 + Telegram + history file | one evening |
| 3 | monitor.py pause-file hook on all entry paths | 30 min |
| 4 | systemd service+timer on Oracle, 16:15 IST; dry-run week in log-only mode (no pause writes) before arming pause action | 30 min + 1 week soak |
| 5 | Saturday digest (append to existing weekly rhythm) | 30 min |

Total: ~1 evening of build + 1 week of log-only soak before REDs can pause.
The soak protects against false-positive teething (thresholds act only after
observed clean on real days).

## 5. Premortem (what could go wrong with the monitor itself)

1. **False REDs from small samples** → N-gates above; soak week; pause is
   entries-only and reversible in one message.
2. **Alert fatigue → ignored reds** → hard cap: one daily line; ambers
   batched weekly; only REDs get detail lines.
3. **Card drift / stale expectations** (strategy edited, card not regenerated)
   → gen_expectations stamps the source-code git hash of the strategy into
   the card; parity flags hash mismatch as AMBER "card stale".
4. **Parity itself dies silently** → the daily line IS the heartbeat; its
   absence is user-visible, and P12 self-checks on the next run.
5. **Timer timezone drift** → Oracle already runs IST (verified); timer uses
   system tz.
6. **DB schema changes break parsing** → checks fail loud (RED "parity
   internal error"), never fail silent — top-level try/except that itself
   sends the failure line.

## 6. Amendment rule

Thresholds in §3.3 are frozen. Changes require a dated decision-log entry in
this file stating what changed, why, and what data prompted it — same
protocol as the news-project spec. Post-incident loosening of a threshold
that fired correctly is forbidden.

  - **P13 "card-staleness"** added per premortem item 3 (card drift / stale
    expectations), deferred from v1. Parity now recomputes each strategy source
    file's current git short-hash (same strategy→file map as
    `gen_expectations.py`, resolved against `_CODE_ROOT`) and compares it to the

    gen_expectations.py"; git unavailable or file unmapped → NODATA. Never RED,

    (false-P1 on holidays / non-market days). `is_market_day` now excludes NSE
    holidays as well as weekends, so P1/P2/P9 return NODATA — not a false RED —
    on a holiday when the monitor is alive but the trading log is legitimately
    empty. The day-counting helpers `trading_days_between` and
    `_n_trading_days_ago` (and, transitively, P4's trading-day-of-month

    touch to P1-P12 behavior and was sanctioned by the premortem itself; it
    tightens, never loosens, any fired threshold. Unknown-year boundary degrades
    gracefully (weekday-only) with a warning surfaced in P1's detail. Source:
    NSE 2026 equity holiday circular, cross-checked against cleartax.in and
    groww.in transcriptions (both agree date-for-date).
- 2026-07-22: **Swing-candidate universe alignment** (47 → 679) shipped in
  `kite/live_monitor/monitor.py` — no §3.3 threshold changed. The
  `rsi_trend_confirmation`/`cci_divergence` expectation cards' `trades_per_month`
  lambdas were computed on the 679-stock retest universe
  (`kite/research/universe_lab.py`'s pond), but the live monitor was scanning
  only NIFTY_50 — a backtest-live parity gap this spec itself exists to catch,
  and P3 would eventually have fired on it as a false trade-rate RED once
  enough live history accumulated. Fix: `scan_swing_candidates` now scans
  `self.wide_daily_cache` (679 symbols, loaded via a new `load_wide_daily_data()`

  `daily_data_cache` only if the wide fetch came up empty (e.g. offline mode).
  Rotation and intraday strategies are untouched — still NIFTY_50 only. The wide
  fetch uses `ThreadPoolExecutor(max_workers=5)`, validated safe by a pre-flight
  rate probe that measured the API clean up to 8 req/s. Also added, matching
  `universe_lab.py`'s retest exactly: a liquidity gate (60d median turnover
  `(close*volume).rolling(60).median()` > 2e7 AND last close > 20) computed
  per symbol at scan time, skipping symbols the backtest's universe would have
  excluded — without it the live scan would trade illiquid names the cards
  were never validated on. Heartbeat now reports `Swing universe: N/679
  loaded` alongside the existing daily/5-min counts.

  threshold changed.**
  - **P14 "wide-universe-freshness" added.** Incident that prompted it: on
    2026-07-23, `load_wide_daily_data()` (the 679-stock swing-candidate fetch
    added 2026-07-22, above) silently returned 0/679; `scan_swing_candidates`'s
    own fail-soft design (`self.wide_daily_cache or self.daily_data_cache`)
    then fell back to the 47-stock NIFTY_50 list with **no check firing** — a
    human found it only by grepping `monitor.log`. P2 never saw this: it reads
    only the narrow `"Daily data loaded for X/Y"` line (the NIFTY_50 fetch);
    it has no visibility into the separate `"Wide daily data loaded for
    X/679 stocks in Zs"` line `load_wide_daily_data()` logs
    (`kite/live_monitor/monitor.py`).
    - **Added as a new check (P14), not folded into P2.** P2's row above is
      specifically "daily cache count at swing scan" for the always-on
      NIFTY_50 universe that P3/P5/P6/P7 depend on; the wide universe is a
      separate, fail-soft, swing-detector-only fetch with a materially
      different failure mode (silent fallback to a smaller universe, not an
      outright data outage). One shared status would blur which universe
      degraded and would change P2's existing meaning and existing tests
      (`test_parity_monitor.py` scenario 4, DEAD TOKEN/DATA, asserts P2 RED
      from the narrow line alone). This mirrors how P13 was layered onto the
      frozen P1–P12 set on 2026-07-21 without touching §3.3.
    - **Thresholds: reuses P2's frozen AMBER <90%/RED <50% verbatim** — see
      the new §3.3 table row. No new number is introduced; this is the
      "reuse, don't invent" instruction from the build brief, applied to a
      second, independently-observed universe-size denominator (679 instead
      of 47). Per §6, extending an already-frozen threshold's *scope* to a new
      check is not a threshold *change* and needs no separate justification
      beyond this note.
    - **Missing-line case is RED, not AMBER**, unlike P2's missing-`"Daily
      data loaded"`-line case (AMBER, "swing scan may not have run yet"):
      `load_wide_daily_data()` runs immediately after the NIFTY_50 daily load
      in the same startup sequence (`monitor.py:load_historical_data`), so by
      the 16:15 IST parity run, total absence of its line means the load step
      itself never executed — a strictly worse signal than a low count, per
      the task brief ("If the wide-load line is absent entirely on a market
      day, that is a RED").
    - Skips itself (NODATA) on non-market days, same gate as P1/P2/P9.
    - New test coverage: `test_parity_monitor.py` scenarios 12–15 (healthy
      623/679 → GREEN, degraded 400/679 → AMBER, collapsed 0/679 → RED,
      missing line on a market day → RED).
  - **`PARITY_TODAY_OVERRIDE` test-only seam added**, closing a *test-suite*
    gap (not a monitor-behavior gap): `test_parity_monitor.py` failed 4/11 on
    Sat/Sun because scenarios 1/3/4/5 assert GREEN/RED on P1/P2/P9, which
    correctly return NODATA on non-market days (the holiday/weekend gate
    shipped 2026-07-22, above) — so the suite was only ever meaningfully
    runnable Mon–Fri. Fix: every `datetime.now().date()`-equivalent call in
    `parity_monitor.py` now goes through one seam function, `_today()`
    (full-datetime counterpart `_now()`, used only for the run's `ts` stamp).
    `_today()` reads `PARITY_TODAY_OVERRIDE` (format `YYYY-MM-DD`); if unset —
    always true in production — it returns the real wall-clock date, so
    behavior is byte-for-byte unchanged from before this entry.
    `test_parity_monitor.py` reads the *same* env var to pin its own `TODAY`
    constant (used to build fixture dates), and forwards it to every
    `parity_monitor.py` subprocess it launches automatically, since
    `run_parity()` already does `env = os.environ.copy()` — no new plumbing
    needed there.
    - **Cannot silently affect production**: (1) default (unset) is always
      the real date — the Oracle systemd timer's crontab/unit never sets this
      var; (2) whenever it IS set, `_today()` prints a loud `WARNING` to
      stderr the first time it's called in the process, naming the pinned
      date and stating it is test-only, so a value left set by accident is
      immediately visible rather than silently skewing a real run; (3) a
      malformed value (not `YYYY-MM-DD`) is ignored with its own warning
      rather than crashing or defaulting to some other date.
    - Verified both ways: full suite (now 15 scenarios) run once with no
      override on a real weekday (15/15 pass) and once with
      `PARITY_TODAY_OVERRIDE=2026-07-24` (a Thursday-free, non-holiday Friday
      — confirmed against `NSE_HOLIDAYS_2026`) on the same real weekday
      (15/15 pass, values shift by the expected one day e.g. P4's "trading-day
      N of month"). As a negative control, pinning the override to an actual
      weekend date (`2026-07-25`, Saturday) correctly reproduces the original
      NODATA-vs-GREEN/RED conflict (7/15 pass, all 8 failures on P1/P2/P9/P14
      scenarios expecting GREEN/RED and getting NODATA) — proof the seam
      genuinely drives `is_market_day`/checks rather than hard-coding a pass.
